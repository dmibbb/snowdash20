# SnowDash Web — техническая спека

Ниже — дизайн-документ, по которому можно писать код. Я постарался описать что и как, но без привязки к конкретным именам классов/файлов на уровне реализации — это уже дело разработки. Спека покрывает всё, что есть в оригинале, плюс отмечает места, где я предлагаю слегка упростить (помечено упрощение).

## 1. Общее описание

SnowDash — 2D-игра с видом сверху на сетке. Игрок (снежок Снежок) ходит по клеткам уровня, ест снег, собирает сундуки, толкает камни и убегает от монстров. Уровень считается пройденным, когда собраны все сундуки. Камни падают вниз под действием гравитации, могут убивать монстров (и игрока, если неудачно встать).

Цель переиздания — сохранить механику и ощущение оригинала 2006 года, но с современной графикой (без масок, PNG с альфой), браузерным звуком и мобильным управлением в перспективе.

## 2. Технический стек

- Язык: TypeScript (strict mode)
- Рендер: Canvas 2D API
- Сборка: Vite (vanilla-ts)
- Звук: HTMLAudioElement (музыка), пул Audio для SFX
- Тесты логики: Vitest (запуск в Node без браузера)
- Без фреймворков (React, Vue, Phaser, PixiJS не используются)
- Деплой: статика (GitHub Pages / Netlify)

## 3. Игровые режимы (экраны)

Конечный автомат верхнего уровня GameMode:

| Режим    | Описание                                                                                                                                           |
| :------- | :------------------------------------------------------------------------------------------------------------------------------------------------- |
| Intro    | Заставка «RGB Team presents…», анимация логотипа. Играет трек 01. Пропускается по любой клавише/клику.                                             |
| Menu     | Главное меню: **Let's Go!** / About / Help! / Exit. Продолжает играть трек 01. Фон — зимний пейзаж, логотип SnowDash сверху, RGB Team внизу слева. |
| Help     | Отдельный экран: сюжетный текст про Санту и мистера Снежка (см. 12.1), кнопка «Main Menu» внизу слева.                                             |
| Playing  | Игровой процесс                                                                                                                                    |
| GameOver | Игрок проиграл или прошёл все уровни. Показывается счёт, рейтинг, кнопка возврата в меню.                                                          |

Переходы:

- Intro → Menu (по таймеру или вводу)
- Menu → Playing: новая игра с нуля (новый Game, score=0, lives=4, levelIndex=0)
- Menu → Help: отдельный GameMode
- Menu → About: модальный оверлей поверх Menu
- Menu → Exit: модальный оверлей «Thanks for playing!» + SFX 29 (Hero Die 4), без закрытия окна
- Help → Menu (Back)
- Playing → GameOver: полноценный GameMode (0 жизней или все уровни пройдены), кнопка Back to Menu
- GameOver → Menu (Game сбрасывается, следующий Start создаст новый)

## 4. Рендер и разрешение

- Логическое разрешение canvas: 800 × 600 пикселей.
- Размер клетки: 40 × 40 пикселей.
- Игровое поле: 20 столбцов × 13 строк = 800 × 520 пикселей.
- HUD: нижняя полоса 20 × 2 клетки = 800 × 80 пикселей.
- Итого: 800 × 600. ✓

Масштабирование: canvas растягивается через CSS (width: 100%, max-width: 1200px, image-rendering: pixelated), логическое разрешение всегда 800×600. Мышь/тач нормализуются с учётом масштаба при необходимости (для меню).

Упрощение относительно оригинала: в оригинале фон повторялся по сетке, HUD рисовался на 1 клетку снизу. У нас HUD — фиксированная полоса 80px, фон тайлится по игровому полю.

## 5. Игровой цикл

- Рендер через requestAnimationFrame (60 fps на мониторе).
- Логика игры тикает с фиксированным шагом 50 мс (20 Hz). В оригинале фиксированного тика не было — главный цикл использовал Sleep(10) с переменным dt (~50–70 fps). Мы перешли на фиксированный шаг ради детерминизма и тестируемости; скорости игрока/монстров/камней пересчитаны под 20 Hz так, чтобы «пиксели в секунду» совпадали с оригиналом.
- Скорости и тайминги анимации задаются в пикселях за тик (см. ниже).
- Не использовать deltaTime для физики — это сломает ощущение оригинала. Только фиксированный шаг.

Один tick():

- Обработать ввод (направление игрока).
- Обновить игрока (move).
- Обновить монстров (move).
- Обновить камни (move).
- Обработать коллизии (игрок ↔ монстр, игрок ↔ камень, монстр ↔ камень).
- Обработать взаимодействие игрока с тайлами клетки, на которой он стоит (Snow → съесть, Chest → собрать). Проверка Wall выполняется в possibleDirection при попытке движения в эту клетку.
- Обновить счёт/жизни/состояние уровня.

Рендер выполняется вне tick() — на каждом кадре rAF, но использует текущее состояние.

## 6. Система координат

- Каждая сущность имеет пиксельные координаты x, y (левый верхний угол спрайта) и клеточные координаты cell = floor(pixel / 40).
- Игровое поле — двумерный массив Cell[][], где Cell — контейнер для статического тайла и (опционально) динамической сущности.
- Пиксельные координаты всегда кратны 40, когда сущность стоит на клетке (в середине клетки, а не в углу — сущность размером с клетку совпадает с клеткой).

Важно: в оригинале «центр клетки» — это верхний левый угол клетки, потому что спрайт 40×40. Следуем этому же упрощению: позиция (x, y) — левый верхний угол спрайта, который совпадает с левым верхним углом клетки.

## 7. Тайлы (статические сущности)

| Символ       | Имя          | Проходимость | Поведение                                        |
| :----------- | :----------- | :----------- | :----------------------------------------------- |
| B            | Wall (ёлка)  | Непроходим   | Просто препятствие                               |
| S            | Snow         | Проходим     | Съедается при входе (исчезает, звук)             |
| C            | Chest        | Проходим     | Собирается при входе (+30 очков, исчезает, звук) |
| P            | Player start | —            | Точка старта игрока                              |
| . или пробел | Empty        | Проходим     | Ничего                                           |

Игрок может стоять на клетке со снегом или сундуком — и «съесть/собрать» её при входе (снег/сундук исчезают, клетка становится Empty).

После того как игрок съел снег/сундук, на клетке остаётся Empty, но на уровне фона может остаться картинка земли (в оригинале фон всегда одинаковый).

## 8. Динамические сущности

### 8.1. Игрок (Player)

Состояния:

- Idle — стоит на клетке, не двигается
- Moving — движется к соседней клетке

Направление: up | down | left | right | stop

Движение:

- Перемещение ровно на 1 клетку (40 px) за 8 тиков (400 мс), т.е. скорость 5 px/тик при фиксированном тике 20 Hz = 100 px/сек = 2.5 клетки/сек. Значение подобрано по ощущению оригинала (там было 2 px × ~55 fps ≈ 110 px/сек); может быть уточнено после плейтеста.
- Игрок не может изменить направление посередине клетки — сначала доезжает до центра, потом начинает новое движение. (Idle → * выбор направления → Moving до соседней клетки → Idle). Это означает, что если игрок движется вправо и игрок нажимает "вверх" посередине клетки, направление не изменится до завершения движения.
- Если впереди стена — движение отменяется, игрок остаётся в Idle.
- Если впереди монстр — игрок умирает (см. 10).
- Если впереди камень (см. 8.3) — либо толкает его, либо блокируется.
- Снег/сундук исчезают в тике, когда игрок находится в Idle и вызывается possibleDirection(). Проверка выполняется для клетки, на которой стоит игрок (не той, куда он собирается идти).

Анимация:

- Для каждого направления — 3 кадра: idle, step1, step2.
- При движении кадры переключаются каждые 5 тиков (250 мс): idle → step1 → idle → step2 → idle → ... (в оригинале было чередование через позиции в клетке — эквивалентно).
- В покое показывается idle текущего направления.
- Начальный кадр при старте уровня — idle вниз.

Очки: Счёт и жизни хранятся в состоянии игры (game.ts), не в Player. Player только читает/инкрементит через методы game.

Жизни: lives, старт — 4 (см. раздел 11).

### 8.2. Монстр (Monster)

Два типа (модели):

| Модель | Имя     | Скорость              | Очки при убийстве камнем |
| :----- | :------ | :-------------------- | :----------------------- |
| 1      | Амёба   | 3 px/тик (60 px/сек)* | 35                       |
| 2      | Спайкер | 3 px/тик (60 px/сек)* | 25                       |

(3 px/tick при 20 Hz ≈ 60 px/сек, что примерно вдвое медленнее игрока — как в оригинале)

Поведение:

- Случайное блуждание по сетке.
- Если впереди препятствие (стена, видимый снег, видимый сундук, камень, другой монстр, край карты) — выбирает новое случайное направление.
- Монстр может ходить только по клеткам empty. Съеденный игроком снег/сундук становится empty — тогда монстр проходит.
- Движется по клеткам, аналогично игроку (но медленнее).
- Анимация: 2–3 кадра на направление, переключение каждые 5 тиков.

Смерть:

- Убит камнем — исчезает, игроку +35 / +25 очков, звук «Enemy Die» (циклически 4 варианта), монстр помечается как killed и больше не обновляется.

Коллизия с игроком:

- При пересечении AABB монстра и игрока — игрок теряет жизнь (см. 10).

Коллизия с камнем:

- Если камень в состоянии Falling или Pushed пересекается с монстром (см. 8.3) — монстр умирает, очки игроку.

Упрощение относительно оригинала: оригинал имел сложную логику «монстр стоит на клетке над камнем и ждёт, пока камень упадёт» — можно упростить до простого AABB-пересечения.

### 8.3. Камень (Stone)

Состояния:

- Idle — лежит на земле/снегу/сундуке
- Falling — падает вниз (или вбок с края)
- Pushed — толкается игроком влево/вправо

Гравитация:

- Если под камнем пустая клетка (Empty) — камень падает вниз.
- Если под камнем стена, снег, сундук, другой камень или граница карты — камень стоит (Idle).
- Снег и сундук держат камень как опору, пока игрок их не съел (соответствует Object::Empty() == !visible в оригинале). После того как игрок съел снег/сундук, клетка становится empty — камень теряет опору и падает.
- Скорость падения: 8 px/тик при 20 Hz = 160 px/сек = 4 клетки/сек.
- Скорость при толкании: равна скорости игрока (5 px/тик = 100 px/сек = 2.5 клетки/сек).

Падение вбок (с края):

- Если камень стоит на другом камне (не на стене, не на снегу/сундуке), и слева или справа от камня на его уровне пусто, и клетка по диагонали (слева-снизу или справа-снизу) тоже пуста, и на камне сверху ничего не лежит, и игрок не стоит в клетке скатывания или прямо над ней — камень падает вбок.
- Условие: слева/справа от камня на текущем уровне пусто, а под тем местом, куда он сдвинется, пусто.
- Это создаёт эффект «камень скатывается с края».
- Скорость при падении вбок: горизонтальный сдвиг на 1 клетку — 5 px/тик (как при толкании); после сдвига вертикальное падение — 8 px/тик.

Толкание игроком:

- Если игрок идёт в сторону камня, и камень в состоянии `idle`, и за камнем есть свободное место — камень сдвигается в том же направлении со скоростью игрока. Игрок идёт вслед за камнем в том же темпе.
- Важно: при толкании НЕ проверяется, может ли камень упасть. Если под толкаемым камнем пусто — он всё равно катится горизонтально, пока игрок держит направление. Это соответствует оригиналу (SetPlayerDirection задаёт камню direction = LEFT/RIGHT, и PossibleDirection катит его горизонтально независимо от пустоты под ним). Гравитация срабатывает, когда игрок отпускает клавишу — камень становится `idle`, и в следующем тике начинает падать.
- Если за камнем стена / другой камень / край — игрок блокируется.

Смерть:

- Если камень в состоянии Falling или Pushed пересекается с игроком — игрок теряет жизнь.
- Если камень в состоянии Falling или Pushed пересекается с монстром — монстр умирает.
- Игрок может безопасно стоять на клетке под висящим камнем, пока тот в состоянии Idle. Как только камень начнёт падать (пересечение с игроком) — урон.

Звуки:

- Начало падения: «Stone Falling» (SFX 36).
- Приземление: «Stone Falled» (SFX 35).
- Толкание: «Move Snow Ball» (SFX 32).

Анимация: один кадр (камень не анимируется).

Упрощение относительно оригинала: в оригинале была сложная система KillMode (счётчик тиков падения) и «безопасных» клеток. У нас — простое правило: (Falling || Pushed) && AABB.intersects(player) → damage.

- **Отклонение от оригинала (UX):** игрок не может войти в клетку, пиксельно перекрытую `falling`-камнем — попытка блокируется. Проверка идёт по AABB камня и целевой клетки, а не через `getCell()`, потому что округление даёт рассинхрон (камень «середине падения» логически уже в следующей клетке, физически занимая часть текущей). В оригинале игрок мог войти в такую клетку и погибнуть от коллизии (`Crossing` + `KillMode != 0`). Мы считаем это плохим UX и блокируем движение.

## 10. Урон, жизни, смерть игрока

- Жизни: старт 4 (MaxLife = 4).
- Потеря жизни: коллизия с монстром ИЛИ коллизия с падающим или толкаемым камнем.
- При потере жизни:

1. Играется звук «Hero Die» (один из 4, циклически).
2. lives--.
3. Если lives > 0 — уровень перезапускается с начала (все объекты на исходные позиции, счёт сохраняется).
4. Если lives == 0 — переход в GameOver.

- Сброс уровня: все монстры на стартовые позиции, камни на стартовые позиции, снег и сундуки восстановлены, игрок на стартовую клетку, toTarget сброшен, направление stop.
- `Game.tick()` вызывает `onPlayerHit()` при коллизии. При `lives > 0` уровень **ресетится** (позиции, тайлы, сущности), но **не перезагружается** — тот же `Level` и `Player`, просто сброшенные. Счёт не меняется.
- При `lives === 0` выставляется `isGameOver = true`, `tick()` больше не выполняется. Отрисовывается GameOver-оверлей.

## 11. Очки и прогрессия

События и очки:

| Событие                  | Очки                                 |
| :----------------------- | :----------------------------------- |
| Съеден сундук            | +30                                  |
| Убит монстр моделью 1    | +35                                  |
| Убит монстр моделью 2    | +25                                  |

Каждые кратные 250 очков: Звук играет при достижении счёта 250, 500, 750, 1000, ... (порог увеличивается на 250 после каждого срабатывания).

Прогрессия:

- 10 уровней.
- Уровень пройден, когда visibleChests == 0 (все сундуки собраны).
- После прохождения: пауза ~2.5 сек, звук «Level Done» (SFX 30), всплывающее сообщение с текущим счётом, загрузка следующего уровня.
- После 10-го уровня: GameOver с максимальным рейтингом (9).

- `Game` владеет списком путей к уровням (`levelPaths`). После `visibleChests === 0` и `+50` очков — `levelIndex++`, `loadLevel(nextIndex)`. Если `nextIndex >= levelPaths.length` — `isGameOver = true`.

Состояние между уровнями: счёт сохраняется, жизни — да (не сбрасываются).

## 12. UI / HUD

Нижняя полоса 800×80 содержит:

- Иконки жизней (слева, x ≈ 100): до 4 иконок игрока (idle-спрайт) в ряд с шагом 20px.
- Надпись «Score» (по центру, x ≈ 300): статичная картинка.
- Число очков (справа от «Score», x ≈ 450): цифры, каждая — отдельный спрайт, шаг 40px.
- Надпись «Level» (x ≈ 620): статичная картинка.
- Номер уровня (x ≈ 720): одна цифра.
- HUD рисуется с Y = 520, высота 80

Оверлеи:

- Pause: по центру экрана надпись «PAUSE» (при нажатии Esc/P).
- Game Over: при lives == 0 — оверлей «Game Over» + сообщение с рейтингом и счётом.

### 12.1. Экраны меню (готово в фазе 8)

### 13.1. Музыка (плейлист)

4 трека, циклическое воспроизведение:

| Трек   | Оригинальное название | Роль         | После окончания играет |
| :----- | :-------------------- | :----------- | :--------------------- |
| 01.mp3 | Midnight Dreams.mp3   | Intro / Menu | 01                     |
| 02.mp3 | Eastern Thriller.mp3  | Игра         | 03                     |
| 03.mp3 | Escapist.mp3          | Игра         | 04                     |
| 04.mp3 | Last Runaway.mp3      | Игра         | 02                     |

Трек 01 звучит на экранах Intro и Menu и зациклен сам на себя. По клику Start он останавливается, и запускается игровой цикл 02→03→04→02, который играет до Game Over или до прохождения 10-го уровня. После этого игровые треки (02, 03, 04) останавливаются, и снова включается 01 (возврат в меню).

Autoplay (текущее ограничение): браузеры блокируют `play()` до первого user gesture. Поэтому Intro в 9.2 беззвучное, первое нажатие клавиши/клик разблокирует аудио и запускает трек 01 на Menu. Целевое поведение — Intro с треком 01: будет реализовано в следующей итерации через splash screen с кнопкой «Start», после которой Intro проигрывается с музыкой. До этого момента Intro остаётся беззвучным как временная мера.

Mute: клавиша M в любом режиме → `audio.toggleMute()`. Регулирует `volume` текущего трека (SFX — в 9.3). Работает и для музыки, и для SFX после их появления.

## 14. Управление

| Клавиша        | Действие                             |
| :------------- | :----------------------------------- |
| ↑ / W          | Вверх                                |
| ↓ / S          | Вниз                                 |
| ← / A          | Влево                                |
| → / D          | Вправо                               |
| Esc / P        | Пауза                                |
| M              | Mute / Unmute                        |
| Enter / любая  | Пропустить интро, подтвердить в меню |
| Клик по кнопке | Действие кнопки                      |

- Enter/Space, Esc/P, M, клики, **любая клавиша в Intro** — edge-triggered.
  - В Menu: Enter = Start. Esc/P/Enter/клик в About/Exit = закрыть модалку.
  - В Help: Esc/Enter/клик на Main Menu = назад.
  - В Playing: Esc/P = пауза.
  - В GameOver: Esc/Enter/клик на Back to Menu = в Menu.
  - В Intro: любая клавиша/клик = скип в Menu.
- Клики нормируются через `getBoundingClientRect` canvas → логические 800×600 (учёт CSS-скейла).
- `getMousePosition()` — continuous, для hover.

Важно:

- preventDefault() на стрелках, чтобы не скроллить страницу.
- keyup/keydown только для игровых клавиш.
- Очистка зажатых клавиш на window.blur (иначе герой «залипает» при переключении таба).
- После клика по кнопке меню — button.blur(), чтобы фокус ушёл с кнопки и клавиатура работала на canvas.

Ввод хранится как набор зажатых клавиш. В каждом tick(), если игрок в состоянии Idle, направление берётся из текущего набора (приоритет: up > down > left > right, если несколько). Если игрок в Moving — ввод игнорируется до прибытия в клетку.

- Intro: любая клавиша/клик — пропуск в Menu.
- Menu: клики по кнопкам. Enter — Start (Let's Go!).
- Help: клик по Main Menu или Esc/Enter — назад в Menu.
- About: клик по OK или Esc/Enter — закрыть.
- Exit: клик по OK или Esc/Enter — закрыть оверлей (остаёмся в Menu).

## 16. Жизненный цикл загрузки

- Инициализация canvas, ctx.imageSmoothingEnabled = false.
- Прочитать level_list.txt — список путей к файлам уровней.
- Создать `Game(levelPaths, fetchLevel)` — Game владеет состоянием и сам загружает уровни.
- `await game.start()` — загружает уровень 0.

**Фаза 7 (текущее состояние):** после старта сразу Playing. Intro, Menu, загрузка ассетов — в фазе 8, звук — в фазе 9.

**Целевое состояние (фаза 8–9):**

- Preload изображений и звуков (Promise.all). Прогресс-бар.
- Запустить Intro → Menu → Playing по Start.
- Остановка трека 01, запуск трека 02 (после клика — autoplay разрешён). Дальше игровой плейлист 02→03→04→02.

## 18. Тестируемость (важно для бэкендера)

Юнит-тесты без браузера (Vitest) должны покрывать:

- Парсер уровня (правильные/неправильные файлы, короче/длиннее 20×13, отсутствие P).
- Level.getObjectFromCell(cell) — все случаи.
- Player.possibleDirection() — стена, снег, сундук, монстр, камень, край карты.
- Player.move() — движение до центра клетки, остановка, смена направления.
- Stone.move() — падение, падение вбок, толкание, приземление на монстра/игрока.
- Monster.move() — случайное блуждание, выбор направления при блокировке.
- Логика счёта и жизней.
- Логика перехода между уровнями.
- Рендер, ввод, звук — не тестируются юнит-тестами (только ручной плейтест).
- Интеграционные тесты (например, Загрузить уровень → симулировать 100 тиков хода вправо → проверить, что съеден снег и собран сундук → проверить переход на следующий уровень).

## 19. Граничные случаи и типичные баги (чеклист)

- Асинхронная загрузка: игра не стартует, пока все ассеты не загружены.
- Автоплей аудио: музыка стартует только после первого клика.
- imageSmoothingEnabled = false — пиксели не мылятся.
- preventDefault на стрелках.
- Очистка зажатых клавиш на window.blur.
- button.blur() после клика по кнопке меню.
- Фиксированный шаг 50 мс — не deltaTime.
- Игрок останавливается ровно в центре клетки (пиксельные координаты кратны 40 в Idle).
- Смена направления игрока — только из Idle.
- Камень не «застревает» на границе карты (проверка x >= 0 && x < cols && y >= 0 && y < rows).
- Монстр не выходит за границы карты.
- Все сундуки собраны → переход на следующий уровень, а не зависание.
- Потеря жизни → полный сброс уровня, счёт сохранён.
- Game Over → рейтинг по номеру текущего уровня.
- Mute работает и на музыку, и на SFX.
- Пауза останавливает tick() целиком (не только ввод). Музыка/SFX приглушаются.
- Что происходит, если игрок стоит на клетке, где был сундук, и нажимает направление в стену? Игрок остаётся на месте, сундук уже собран.
- Что происходит, если два монстра пытаются занять одну клетку? Они выбирают новое направление.
- Что происходит, если камень падает на другой камень? Верхний камень останавливается.
- Intro можно пропустить любой клавишей/кликом (не ждать 3 секунды).
- Exit не пытается закрыть окно (браузер не даст), показывает оверлей.
- Menu → Playing пересоздаёт Game (счёт/жизни/уровень с нуля).
- About — модальный оверлей, не отдельный режим.

## 20. Non-goals (что НЕ входит в первую версию)

- Мультиплеер.
- Редактор уровней.
- Онлайн-таблица рекордов.
- Мобильные жесты (свайпы) — только клавиатура + клики (тач-кнопки — во второй итерации).
- Сохранение прогресса между сессиями — во второй итерации (через localStorage).
- Локализация (RU/EN) — только русский или только английский, на выбор.
- Скины персонажа, кастомизация.

- Музыка: трек 01 играет на Intro/Menu и зациклен на себя; по Start запускается игровой цикл 02→03→04→02; после Game Over / 10-го уровня возврат к 01. Стартует после первого клика (требование браузера).
- Все SFX из таблицы 13.2 воспроизводятся.
- Пауза (Esc/P) работает.
- Mute (M) работает.
- npm run build собирается без ошибок, npm run preview показывает рабочую игру.
- Юнит-тесты логики (раздел 18) зелёные.
- Игра не падает через 30–40 секунд (утечка DC из оригинала не воспроизводится — по определению).
- Полный цикл Menu → Playing → (GameOver или конец уровней) → Menu → Playing замыкается без F5.

## 23. Открытые вопросы (обсудить перед стартом)

- Спрайт-листы vs отдельные PNG. 12 файлов на игрока — многовато. Можно склеить в один атлас. Решение: на первую итерацию — отдельные PNG, проще.
- Точное соответствие индексов анимации. В оригинале индексы imageArray[6..13] — нужно сопоставить с up_step1, up_step2, и т.д. Это выяснится при конвертации.
- Графика. Оставить пиксель-арт 2006 года как есть (аутентично) или перерисовать? Решение: на первую итерацию — оригинал, конвертированный в PNG.
